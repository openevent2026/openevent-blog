最近几年，Agent 项目层出不穷——从早期的 LangChain，到前段时间爆火的 OpenClaw。但热潮之下，一个尴尬的事实始终存在：真正在 Agent 架构层面沉淀为通用基础设施的，少之又少。

很多团队仍在各自的问题域里，反复重建工具层、状态层、通信层、控制层与运行时骨架。Agent 产品更新很快，但支撑它们长期运行的工程地基，却常常像临时脚手架一样，每隔一段时间就要推倒重来。

## 失控的工程基座

眼下 Agent 产品、运行时和编排框架层出不穷，但沉淀下来的通用基础设施却少得可怜。现在 Agent 代码基本靠 AI 生成，VibeCoding 确实把开发速度拉上去了，可代码质量还远没到能放心托付的地步，共性缺陷仍在不同项目中反复出现，多家主流的 Coding Agent 到现在仍然很容易因网络抖动而陷入卡死或中止状态。随着 VibeCoding 成为主流，人类工程师对 Agent 项目的代码质量逐渐失去掌控。

Agent 系统中存在两类截然不同的模块，一类是 AI 核心层——模型、策略、记忆、任务拆解方式——它们受模型能力演进影响极大，需要快速迭代、持续实验；另一类是工程基础设施层——工具执行、文件系统、消息通信、权限、审计、人工接管入口——这些属于确定性工程，应当长期稳定、边界清晰、行为可预期。对大多数 Agent 产品而言，前者是差异化亮点，后者却只是不得不承担的维护负担。

造成当前局面的根源在于，这个领域至今缺少一层被反复复用、被长期维护、被行业共同积累的基础设施层。MCP、A2A 等协议固然在局部接口上达成了共识，但它们只是"接口"，而非"主板"。即便协议统一，每套 Agent 框架仍需重新实现整套适配与运行时。整个生态缺少一个标准中枢——一个能够将 Agent 系统的各模块解耦为独立维护单元、并提供稳定连接与组合能力的协作基础。没有这一层，工程师们就无法在共享的地基上，共同建设高质量的 Agent 生态。

这样一个共识基座带来的好处，不只是工程质量和开发效率的提升。更重要的是，它让人类重新拿回了对智能系统的控制权——既建立起跨团队、跨组织协作的公共契约，也向使用者和监管者作出可验证的确定性承诺。当底层基础设施收敛成一层稳定、开放、可审计的共识层，工程师才不会成为面对黑箱的焦虑旁观者，而是拥有明确介入界面的治理参与者。

确定性工程必须原生地承载这种承诺：每一次工具调用留下不可篡改的审计记录，每一次状态迁移都暴露可观测的上下文边界，每条自主决策链路都预留人工审查与紧急制动的入口。地基之下没有魔法，只有契约；基础设施的最高职责，是保障人类始终保有"审计"与"拔电源"的底线安全。而这样的承诺，是决不能建立在每个智能系统各自的 VibeCoding 之上的。

## 日志先行

那么，这种可审计、可治理的确定性承诺，应当由何种机制来承载？当前大多数 Agent 系统的现实是，模型推理的轨迹、工具调用的参数、权限决策的上下文、人工接管的操作，这些关键信息散落在各处——有的仅存于易失的会话窗口，有的混在向量缓存之中，有的被打印到标准输出，有的则写入彼此隔离的结构化日志文件。一旦 Agent 行为偏离预期，工程师往往需要在不同介质之间拼凑因果链。审计在此沦为事后取证，而非系统内生的能力。

一个自然的思路是借鉴日志先行（Write-Ahead Log）：任何状态变更，先记录，后生效。日志是唯一的真相源，数据库文件不过是日志的物化视图。将这种思路移植到 Agent 基座：每一次工具调用、每一次模型决策、每一次权限校验、每一次人工策略覆盖，都必须先写入持久化的、带全局时序标识的事件日志，而后才允许真正作用于系统状态。如此，可观测性便不再是事后贴补的补丁，而是从第一天起就长在系统骨架之中。

沿此方向进一步推演，架构的重心或许值得重新审视。我们向来习惯以会话状态或上下文窗口为中心组织存储，但如果将不可变的日志流置于中枢，让所有模块的对外交互都收敛为对日志的追加与消费，系统的面貌将大不相同。各个有状态模块不再是独立的孤岛，而不过是同一条日志流的物化视图；状态不再散落为彼此隔离的快照，而是对统一日志流的不同投影；模块间的协作也不再依赖直接的 API 调用，而是通过消费与产生日志事件来间接完成。

由此可以进一步设想：这个共识基座的中枢，不应当是某个具体的运行时或协议网关，而应该是一条持久化、不可变、全局有序的事件日志。模型推理、工具执行、权限校验、人工介入——所有模块都围绕这条日志展开协作。它既是系统的记忆，也是人类握住的把手；既是模块间解耦的边界，也是行业共同积累的载体。这样的基座，或许正是 Agent 生态从各自为战走向协作共建的起点。

## 从会话驱动到事件驱动

日志流提供了统一的数据层，但要让 Agent 真正持续自治，还需要重新审视系统的运转方式。当前 Agent 系统普遍采用的会话驱动范式，本质上是将 LLM 的产品形态直接照搬到了架构层。大模型的原生接口是对话流，ChatGPT 的成功又强化了这种交互直觉，于是行业习惯性地把"会话"当作 Agent 的默认骨架。这在信息获取场景下无可厚非，但 Agent 系统解决的是行动执行问题——它需要持续感知环境、响应异步变更、维护跨周期状态。用对话循环来承载持续自治的需求，是一种根本性的架构错位。

会话驱动将人类输入作为系统的心跳，把交互边界与系统感知边界混为一谈。当 Agent 等待输入时，它与真实环境之间实际上是断开的：文件系统变更、外部服务回调、依赖资源迁移，这些都无法自动穿透会话围墙触达 Agent。为了弥补这一断裂，系统只能退化为轮询或定时扫描——这种被动拉取模式在工程上显然是低效的：轮询间隔直接决定感知延迟，高频浪费资源，低频造成滞后，面对快速连续变更时容易读到中间态或丢失短暂窗口。Agent 因此无法建立精确的环境因果模型，其决策只能建立在并不准确的快照之上。

这种架构惯性是产品形态向技术层渗透的自然结果——当系统以会话为骨架，会话输入便成为了默认的时钟源。但在需要持续环境感知的 Agent 系统中，文件变更、外部回调、定时信号与用户提问，本质上都是同等的状态变更输入。抓住这个本质，系统的核心抽象便不应是会话，而应是事件：所有输入源以统一的不可变形式进入日志流，Agent 基于事件的消费与响应来推进状态。会话退居为事件流上的一种视图投影，Agent 也从等待提问的应答器，转变为与环境持续对齐的自治系统。

把握住事件驱动这个本质，就能在保留会话交互体验的同时，将系统从对话轮次的硬约束中解放出来。当事件成为基座的统一语言，所有状态变更——会话输入、文件变更、外部回调——都以同等地位进入日志流，Agent 得以持续与环境保持精确对齐。会话可以继续承担产品层的沟通职能，但不再是 Agent 运行的中枢。以事件驱动作为 Agent 运行的核心抽象，Agent 工程才能从精巧的 Demo 切入广大复杂的真实场景。

## OpenEvent

基于事件驱动与日志先行的思路，我发起了 OpenEvent 项目。它无意成为又一个端到端的 Agent 产品，而是尝试提供一层确定性基座——将事件流作为系统的统一真相源，让工具执行、状态管理、通信协调与审计治理，都建立在同一套不可变日志之上。我希望，围绕这套最小化的确定性中枢，不同的 Agent 框架、工具链与运行时能够找到协作的基础，将分散在各自项目中的工程经验，沉淀为可被复用、可被审计、可被治理的公共基础设施。
